## 1. Assessment <a href="#section-001" id="section-001"></a>

The project's primary goal is verifiable prediction, reasoning, generation, or control capabilities under explicit task, observation, and resource conditions. Full reproduction of every existing model's computation is not a prerequisite. Component coverage, constructible compatibility, and universal approximation cannot directly guarantee task performance.

This document retains expressivity boundaries, counterexamples, and compatibility constructions as an appendix for consultation as needed; it is no longer a model-implementation roadmap that must be completed soon. See [49 Capability-First Task Cards](49.md) for the main roadmap and [48 Function Spaces and Constrained Solution Spaces](48.md) for mathematical assessment.

Prioritize graph and temporal representations, real prediction-error feedback, local adaptation, and stability with explicit applicability. Enable attention, addressable memory, and higher-order representations according to task bottlenecks; separately validate benefits of implicit solves, generalized geometry, and persistent evolution. Original-model import and operator-by-operator compatibility primarily serve compiler/Aegis-X engineering needs and should be implemented when actual migration tasks arise.

## 2. Five Types of Generality Must Not Be Confused <a href="#section-002" id="section-002"></a>

| Level | Meaning | Current status |
|---|---|---|
| Interface generality | Can call different models and pass data | Design interfaces exist; calling external models is not internal simulation by this model |
| Representational generality | The architecture family can represent target functions or approximate them to specified errors | Potential exists, but fixed graph/memory/symmetry configurations have limits; full coverage is unproved |
| Computational generality | Can represent sequences, branches, loops, states, and expandable storage | Explicit program semantics, addressable storage, and execution constructions are currently missing |
| Learning generality | Can obtain required capabilities through given data/optimization processes | No guarantee; differing objectives and data requirements cannot be omitted |
| Practical generality | Acceptable cost, sample demand, and latency at equal quality | Requires measurements for every task; cannot follow from expressivity |

Existing Transformer universal-approximation research also has conditions concerning continuous functions, input domains, sequences, and approximation metrics; it does not prove that one fixed set of weights learns every task. [Yun et al.](https://arxiv.org/abs/1912.10077)

Idealized computability generally considers growable resources; no fixed device with finite precision, finite storage, and fixed deadlines can exactly solve tasks of arbitrary size. Dynamic growth allows resource limits to change but does not eliminate resource requirements.

## 3. Concrete Limitations and Counterexamples <a href="#section-003" id="section-003"></a>

### 3.1 Graph Messages Do Not Automatically Provide Every Graph-Reasoning Capability <a href="#section-004" id="section-004"></a>

Consider a configuration without extra position/identity/higher-order features, with identical initial node features and shared first-order neighborhood aggregation. In a six-node cycle and two disconnected triangles, every node has two neighbors of the same type. At every layer all nodes receive identical representations, and the same pooling over six nodes produces identical outputs, although the graphs have different triangle counts. This configuration therefore cannot distinguish them.

This is a counterexample for a restricted message-passing configuration, not an impossibility proof for the entire SGD system including external tools. GNN expressivity research explicitly identifies limits of neighborhood aggregation. [Xu et al.](https://arxiv.org/abs/1810.00826) Increasing hidden dimensions or repeating identical aggregation does not automatically repair this; structural features, higher-order relationships, subgraph operations, or other computational paths are required.

### 3.2 Fixed States Cannot Losslessly Store Arbitrarily Long Histories <a href="#section-005" id="section-005"></a>

Assume all available historical memory totals B bits, with no external storage or input rereading, and the past is compressed only into an SSM. Arbitrary binary histories of length T>B have 2^T possibilities, while memory has at most 2^B states; at least two different histories map to the same memory. If a later query asks for a bit where they differ, the model cannot answer exactly for every input.

This is a finite-precision information-capacity limit. Theoretical constructions with infinite-precision real states do not establish actual BF16 chip capabilities. Growable, addressable memory or input rereading is needed, rather than merely more training time. Neural controllers with external read/write memory already have research precedents. [Neural Turing Machines](https://arxiv.org/abs/1410.5401)

### 3.3 Symmetry and Stability Are Helpful but Restrictive <a href="#section-006" id="section-006"></a>

A strictly rotation-invariant scalar head cannot simultaneously output arbitrary scalars depending on the fixed world x-axis; set processing without positional encoding cannot directly distinguish all ordered sequences. Relevant input conditions can alter task symmetry, but must be explicitly defined. High-dimensional Euclidean equivariance remains a specific constraint, not unrestricted function representation.

Likewise, forcing every internal update to contract or V for every physical state to decrease excludes some memory, oscillatory, chaotic, or expanding dynamics. Document 44 already requires separating stability objects; general-purpose modes should constrain numerical and execution conditions rather than arbitrarily change target-model functions. Inapplicable V checks may still be recorded as inapplicable, without forced projection.

### 3.4 Current “Optional Attention” Is Insufficient as a Transformer Compatibility Specification <a href="#section-007" id="section-007"></a>

2026-09-13 addition: [Transformer operator and architecture comparison](../guide/transformer-comparison.md) distinguishes defined basic operators, optional U02/U03 capabilities, and modern-variant contracts still to be specified; it does not report new implementation results.

B07's mention of cross-attention and B02's external-encoder interface do not define the full combination of multihead self-attention, causal masks, positional encoding, normalization, layerwise residuals, token logits, and KV caches. Current D03 fixed sum/mean aggregation is also not QK-conditioned row-normalized attention.

### 3.5 Growth, Implicitness, and High Dimensions Do Not Automatically Supply Missing Primitives <a href="#section-008" id="section-008"></a>

Trees can search only the space of subunits they can construct; without random-access storage or attention primitives, the name “growth” does not guarantee their discovery. Implicit layers additionally require equations, solves, and root-selection semantics. Larger states, deeper iterations, and more general metrics expand some capabilities but do not replace construction and validation.

## 4. Extension Recommendations: Eight Internal Capability Packages <a href="#section-009" id="section-009"></a>

U01–U08 are internal capability specifications selected as needed, retaining 72 top-level IDs; they are neither eight newly trained networks nor an all-required implementation list. Validation below applies to selected capabilities and does not specify main-roadmap order.

| Capability package | Parent units | Content and interfaces to specify when selected | First validation |
|---|---|---|---|
| U01 Typed computational graphs | C01/C08, F04, H07 | Distinguish data graphs from operator graphs; Tensor/State/Control edges, shape/dtype, parameter sharing, branch/loop semantics | Assemble a small MLP operator by operator with original weights and compare outputs |
| U02 Global relations and order | B02/B07, D02/D03, E08 | Multihead QKV, rowwise softmax, causal/cross masks, positional encoding, global or sparse connections | Transformer blocks and order-sensitive tasks |
| U03 Addressable working memory | D04, F08, H02/H07 | Exact address read/write, content retrieval, KV caches, stacks/sequence buffers, lifetimes, and expansion policies | Delayed copying, index queries, long-sequence rereading |
| U04 Dense and discrete primitive library | B, D06, F04, H07 | Target-model activations, convolutions, normalization, comparison/selection, gating, tensor rearrangement | Layerwise semantic comparisons for CNNs, LSTMs, and hard trees |
| U05 Higher-order and representation strategies | C01/C05/C07, D02/D07/D08 | State choices for points/edge pairs/subgraphs/hyperedges; scalars/vectors/tensors and group actions | Restricted-GNN counterexamples, chirality, and tensor-output tests |
| U06 Probabilistic generation and objective library | E02/E07, G01/G03 | Specialized configurations for autoregressive distributions, noise schedules, sampling, variational/adversarial/value/policy objectives | Reproduce small diffusion, probabilistic regression, and policy objectives |
| U07 Configurable constraints and execution semantics | L01–L08, H03/H04 | Observation/correction modes; constraint domains; compatibility paths preserving target outputs; random-number and precision contracts | Additional layers do not change outputs in same-weight compatibility mode |
| U08 Constructive import and conformance testing | G07, H07/H08 | Target graph/parameter import, operator coverage, output/gradient/state differences, cost reports | Bounded model-coverage inventory and individual pass records |

Model working memory in U03 differs from G05's offline replay library and H02's calls to complete external models. Read/write rules can first be deterministic, with learned addressing validated later. A single summary token or approximate vector-database retrieval does not guarantee arbitrary exact index queries.

U05 should not force higher-order states onto every graph; costs may grow rapidly with order. Adding node IDs can break some symmetries, but must specify whether this violates required relabeling invariance. Higher-order tensors and higher coordinate dimension n are different concepts.

## 5. Constructing Existing Models Rather Than Merely Saying They Can Be Simulated <a href="#section-010" id="section-010"></a>

| Target model family | Construction path | Limitations still requiring specification |
|---|---|---|
| MLP/residual networks | U01/U04 configure linear maps, target activations, and residuals; bypass graph/time/projection paths | Default SiLU is not an exact substitute for all target activations |
| CNN/U-Net | Grids with displacement-type-shared convolution kernels, or native convolution; configure padding/stride/skip/resampling | Graph messages can express local linear convolution without matching execution efficiency |
| RNN/LSTM/SSM | Ordered state updates, corresponding gates and caches; shared temporal parameters | The current simplified diagonal SSM is not an original-parameter importer for arbitrary LSTMs |
| Transformer/ViT/LLM | U02+U03 configure positions, QKV, masks, layerwise FFN/normalization, logits, and caches | Tokenizers, positions, and numerical semantics must match; external B02 calls do not count as internal compatibility |
| GNN/EGNN/higher-order graphs | Select corresponding data graphs, messages, reductions, and typed representations | First-order graphs cannot replace all higher-order graph networks |
| Trees/random forests/MoE | Comparison routing, branch experts, sampling/ensembles, top-k, and weighted combination | Forest ensembles and neural MoE have different training rules |
| Diffusion/flow/VAE/GAN | Explicitly register generated variables, schedules/sampling, and required networks/losses | Outputting a noise vector is not a complete generation algorithm |
| Neural ODE/DEQ/optimization layers | Equations, solves, gradient contracts, and fixed versions from 45 | Evaluate by solver tolerances/distributions rather than arbitrary bitwise equality |
| Kernel methods/nearest neighbors/probabilistic graphs | Kernels and support samples, retrieval or factor messages, and algorithm control | Explicit sample/factor storage is required; not everything fits into a fixed SSM |

This table is candidate coverage for optional compatibility engineering, not a core-model development requirement or existing support inventory. Replace “all models” with a versioned target set; when new models contain unimplemented operators or new state semantics, record unsupported and extend constructors rather than continuing to claim coverage.

### 5.1 A Checkable Transformer Construction Example <a href="#section-011" id="section-011"></a>

Let H be ordered token features; in a selected head compute

$$
Q=HW_Q,\quad K=HW_K,\quad V=HW_V,
$$
$$
A=\operatorname{softmax}_{row}(QK^T/\sqrt{d_k}+M),\quad Y=AV.
$$

Treating tokens as nodes, position pairs allowed to attend as edges, and A as edge weights constructs this operation in a graph-style computational framework. But global connectivity, rowwise normalization, multihead concatenation, and position/mask semantics are required; this is not directly equivalent to current fixed sum/mean aggregation. Then perform projection, residuals, normalization, and FFN in the target order. [Original Transformer paper](https://arxiv.org/abs/1706.03762)

If the target uses other positional encodings, normalization, or attention variants, import their definitions individually. Disable equivariant geometry branches; stability checks run in output-preserving diagnostic mode. Align training dropout and sampling through random states. Fully connected attention may retain quadratic interaction cost; wrapping it in “graphs” or “SSMs” does not justify linear-complexity claims.

## 6. What Can Be Proved <a href="#section-012" id="section-012"></a>

One may attempt a finite construction proposition: given a target model's finite computational graph, if every primitive, parameter, state update, branch/loop, and numerical semantic has a corresponding implementation, executing in the same dependency order allows overall semantic correspondence to be established by nodewise induction. Floating-point rounding, approximate primitives, stochastic processes, and solver tolerances require separate error analysis.

This proves constructible compatibility for a specified model set, not that a new network automatically learns the target models, nor an efficiency theorem. Adding an arbitrary program interpreter primarily provides capabilities of a computing system; these must not be repackaged as original general intelligence of the SGD learning algorithm itself.

Continuous-function approximation propositions also require fixed input spaces, function classes, error metrics, and growable model sizes. Continuous neural networks cannot uniformly approximate all discontinuous hard-decision functions to arbitrary accuracy on continuous domains containing discontinuities; exact hard-tree behavior requires comparison/branch primitives, or explicitly approximate it only on finite input sets/under suitable distributional errors.

Even if every target model has some configuration, this does not imply that one fixed set of weights simultaneously implements all targets. Task conditions, sufficient capacity, training data, and selection rules are needed; automatically discovering suitable configurations is an additional research objective of the evolution mechanism in 46.

## 7. Coexistence with the Existing Core <a href="#section-013" id="section-013"></a>

**Task configurations take priority:** Build models directly from inputs, outputs, constraints, and error metrics. First establish minimal fixed-graph/state baselines, then select equivariant priors, attention, working memory, implicit refinement, or expert growth from evidence. Compare quality and total costs for each; starting from compatible models is not required.

**Compatibility configurations as needed:** Construct target models from original operators, parameters, and states only when migrating existing weights or validating execution backends, avoiding additional operations that rewrite semantics. Success in this engineering task is not innovation in SGD learning mechanisms, and missing compatibility does not negate task capability.

Dynamic trees should select registered, trainable candidate subgraphs; expanding candidate libraries must account for search, training, migration, and old-task degradation costs together. Unlimited time and growth are not actual deployment conditions.

## 8. Validation Roadmap: Capabilities First, Compatibility Tests as Needed <a href="#section-014" id="section-014"></a>

1. Select a real task and corresponding small mathematical task, specifying observable information, constraints, solution-selection rules, quality norms, and resource budgets.
2. Establish baselines with credible reference solutions or frozen test sets. Distinguish observation/discretization, representation, learning, and numerical errors rather than attributing all errors to insufficient capacity.
3. Add one capability addressing a bottleneck at a time, comparing quality–cost under identical data splits and tuning budgets; use this document's structural counterexamples to check the targeted limitation.
4. Once fixed-structure capabilities suffice, compare net benefits of local refinement, persistent growth, replay, and pruning, checking long-term forgetting and stability.

Near-term priorities follow task-error diagnosis. Exact long-history rereading triggers U03; global-relation/order bottlenecks trigger U02; first-order graph indistinguishability triggers U05; multiple-solution or distribution tasks trigger U06. Constraint applicability U07 should be specified with each task. Complete model import through U01/U04/U08 is an engineering branch undertaken only when needed.

For actual compatibility tasks, separately record model_id/version, supported primitives, input limits, precision, parameter/state mappings, output/gradient errors, unsupported operators, and costs. Fixed-weight layerwise comparisons may serve engineering acceptance, but are not prerequisites for scientific-task training.

## 9. Research Claims and Limitations <a href="#section-015" id="section-015"></a>

SGD-Net is positioned as a model family selecting spatial relationships, memory, constraints, and adaptive computation by task. Its central hypothesis is that credible prediction-error and cost feedback can drive structural or computational adjustments that yield reproducible benefits on some tasks. Implementation and experimental validation of this hypothesis remain pending.

Expressivity boundaries determine which capabilities merit additions; function/operator spaces and numerical error analysis determine how to add them. Quality, learnability, cross-task generalization, and execution efficiency require separate evidence, rather than counts of simulated models or components. Without evidence, do not claim coverage of every AI architecture or universal superiority to existing methods.
